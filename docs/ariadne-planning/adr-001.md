# ADR 001 — planning branches from a retained reviewed Core state

Register `demand_contract_screening` / `0.1.0` / `ariadne.plan.demand_contract_screening.v0_1_0` as a separate exact deterministic executor. Do not extend the financial semantics of Close v0.1/v0.2 or the scalar demo model.

The observed state is the exact existing Core version bound to a saved reviewed result. Add only a narrowly reviewed demand-fact intake record shape; Close may preserve these as unsupported component observations. Planning derives supported facts and contextual reference bindings from those frozen records. Originals, source confirmations and evidence remain in existing storage/Core chains. No schema or second source of truth is required.

Saved assumptions and scenarios use existing Core primitives. Scenario metadata records its baseline result and optional parent result for branching. Existing workspace transaction receipts provide retry safety. Private planning paths reuse normal operator/workspace checks and development preflight before request body consumption. Replay uses exact registered metadata and frozen source/rule inputs.

Authority and tariff applicability are separate from software execution. The implementation is a bounded historical normal-regime screening model; explicit assumptions and partial coverage remain part of every result. No recommendation, tax reconstruction or commercial activation follows.

## Addendum — 2026-11-17: preserve 0.1.0, register 0.1.1

Before editing the executor, read-only inspection of the local retained evaluation databases found five persisted `demand_contract_screening` 0.1.0 ModelRuns. Empty/absent identity matching and whole-baseline period rejection change executable outputs, so replacing the implementation under that frozen identity is unsafe.

Preserve `ariadne_planning_engine.py` byte-for-byte (SHA256 `797075e3e90fd74b56669dd632b0a2b89999dcdb8630581e1b5c1bc4d5db62cc`). Add `ariadne_planning_engine_v0_1_1.py`, semantic version `0.1.1`, implementation `ariadne.plan.demand_contract_screening.v0_1_1`. Core dispatch requires exact version, implementation, input/output contracts and execution policy for either executor; unknown or inconsistent metadata is rejected. This follows the existing versioned Close executor pattern without modifying Close or scalar semantics. Separate executor code intentionally avoids coupling future corrections to retained behavior.

The Planning service selects 0.1.1 only for new previews/saves/duplicates. Existing Core model registration appends a model version on the next authorized save; no schema migration, data backfill or rewrite is needed. Both versions retain the same authority policy and financial formula. A duplicate of an old scenario is a new 0.1.1 calculation with a parent reference, not a rewrite of the parent's output. Historical list/read/export/replay use retained lineage rather than revalidating inputs with the new eligibility rules. New execution still validates the baseline.

Exact replay preserves what a historical run computed, including an incorrect 0.1.0 coverage decision. It does not certify that historical result as financially valid. Correcting one requires a new calculation. No existing local evaluation records were rewritten; checks used read-only transactions. This task does not add a general migration or warning UI for old defective runs.
